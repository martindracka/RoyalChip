# Security

This document explains how Royal Chip Casino protects its data, which attacks were considered,
and where each protection lives in the code. Chips are play money, but the project treats them
as if they were valuable – the leaderboard is only fair if nobody can fake a balance.

---

## 1. The main rule: the browser is not trusted

Anything that runs in the browser can be read and changed by the user (DevTools, a proxy, or simply
calling the Appwrite REST API with their own session). So:

- **The browser may only *read* data and *ask* for actions.**
- **Every change of chips happens on the server**, in the Appwrite Function `casino`
  ([functions/casino](../functions/casino)). It runs with a server key and decides the result itself.
- **The database permissions refuse everything else**, so calling the API directly does not help.

```
 Browser (Vue)                       Appwrite
 ─────────────                       ────────────────────────────────────────────
 reads games, promotions,  ───────►  TablesDB  (permissions: read only for players)
 profiles, own bets

 "I bet 100 on red"        ───────►  Function "casino"  (runs on the server)
                                       │  userId from Appwrite header (cannot be faked)
                                       │  validates input, stake, game limits
                                       │  draws the random result (crypto RNG)
                                       │  atomic balance change, writes the bet
 result + new balance      ◄───────    ▼
                                     TablesDB  (written with a short-lived server key)
```

### Before and after

The first version of the project ran the games in the browser and let players update their own
profile row. A player could open the console and set `balance: 1000000`, or create fake bets and
claims. This was listed as a "known limitation". It has been fixed:

| Before | Now |
| --- | --- |
| Result decided in the browser | Result decided in the Function with `crypto.getRandomValues` |
| Player had `update` permission on their profile | Players have **read-only** access to `profiles` |
| Player could create `bets`, `claims`, `referralRewards` rows | Only the Function can create them |
| Blackjack deck was in the browser memory | Deck and the dealer's hidden card stay on the server (`blackjackRounds`, no permissions) |
| Invite reward checked in the browser | Function checks that the friend really joined through the link and wagered enough |

## 2. Who may do what (enforced by Appwrite, not by the UI)

Defined as data in [scripts/schema.js](../scripts/schema.js) and applied by `npm run setup:appwrite`.

| Table / bucket | Guest | Player | Editor | Admin | Casino Function |
| --- | --- | --- | --- | --- | --- |
| `games`, `promotions` | read | read | read, create, update | everything | read |
| `profiles` | – | read | read | read, update, delete | read, create, update |
| `bets` | – | read **own** rows | read own rows | read all, delete | create |
| `claims`, `referralRewards` | – | read **own** rows | read own rows | read all, delete | create |
| `blackjackRounds` | – | – | – | – | read, create, update |
| Storage `game-images` | read | read | upload, replace, delete | everything | – |
| Execute Function `casino` | – | yes | yes | yes | – |

- **Roles are Appwrite user labels** (`admin`, `editor`). Labels can only be changed with a server API key
  ([scripts/set-role.js](../scripts/set-role.js)) – a player can never make themselves admin.
- **"Own rows"** = the Function creates the row with a row-level permission `read(user:<owner>)`.
  Nobody receives `update` on bets → the history cannot be edited.
- **The Function's key** is generated by Appwrite for each execution and limited to the scopes
  `rows.read`, `rows.write`, `users.read` (no permission to change tables, users or settings).

The UI (hidden buttons, [src/lib/roles.js](../src/lib/roles.js)) and the router guard
([src/router/index.js](../src/router/index.js)) only make the app pleasant to use. The real protection
is the table above.

## 3. Attacks that were considered

Every row has an automated test in [tests/server.test.js](../tests/server.test.js) or
[tests/function-entry.test.js](../tests/function-entry.test.js) that runs the real Function code.

| Attack | What stops it | Where |
| --- | --- | --- |
| Set my own balance via the API | No `update` permission on `profiles` for players | `schema.js` |
| Create a profile with 1,000,000 chips | No `create` permission; the Function sets the starting balance | `actions/profile.js` |
| Send `payout: 99999` or my own "result" | The Function ignores it and computes the result itself | `actions/games.js` |
| Bet more than I have / negative / decimal / text | `validateStake` on the server + `balance` column has `min: 0` | `shared/rules.js` |
| Send 5 bets at once to spend the same chips twice | Stake is taken with an **atomic** `decrementRowColumn(min: 0)` | `actions/wallet.js` |
| Bet on a hidden game or outside its min/max | Function loads the game and checks `isActive`, `minBet`, `maxBet` | `actions/games.js` |
| Peek at the blackjack deck / hidden card | Stored in `blackjackRounds` with **no** permissions; response contains only visible cards | `actions/blackjack.js` |
| Press "Stand" several times in parallel to be paid twice | Round is closed with an atomic decrement of `open` (1 → 0) before paying | `actions/blackjack.js` |
| Claim a promotion twice (also in parallel) | Unique index `(userId, promotionId)` → second insert fails with 409 | `schema.js`, `actions/rewards.js` |
| Claim an expired / switched-off promotion, or change its amount | Function checks dates and `isActive`, amount comes from the database | `actions/rewards.js` |
| Claim an invite reward for someone who is not my friend | Function checks `friend.referredBy === me` and `totalWagered >= 500` | `actions/rewards.js` |
| Farm invite rewards with fake accounts | Max. 20 rewards per player, friend must wager 500 chips first | `shared/rules.js` |
| Invite myself | Code must belong to **another existing** player | `actions/profile.js` |
| Pretend to be another user | User ID comes from the `x-appwrite-user-id` header set by Appwrite. Headers starting with `x-appwrite-` cannot be set by the client | `main.js` |
| Unknown or weird actions / huge request body | Allow-list of actions, payload must be an object, body max 2,000 chars | `handler.js`, `main.js` |
| Impersonate a player on the leaderboard | Unique index on `username`; usernames limited to letters, digits, `_ . -` and space | `schema.js`, `shared/rules.js` |
| Make myself admin | Labels can only be set with the server API key | `scripts/set-role.js` |
| Open `/admin` as a player | Router guard → *No access*; and the database refuses the writes anyway | `router/index.js` |
| Learn internals from error messages | Only messages written for players are returned; everything else is "Something went wrong" and logged in the Appwrite console | `main.js` |

## 4. Browser-side protections

| Topic | Protection |
| --- | --- |
| **XSS (injected scripts)** | Vue escapes all `{{ }}` output; the project uses **no `v-html`**. Usernames are restricted on the server as well. |
| **Content Security Policy** | The production build gets a CSP `<meta>` tag ([vite.config.js](../vite.config.js)): scripts only from our own domain, network requests only to our Appwrite endpoint, no plugins (`object-src 'none'`). Even injected HTML could not load a foreign script or send data elsewhere. |
| **Open redirect** | After login, `?redirect=` is accepted only for internal paths – `//evil.com`, `/\evil.com` and control characters are refused ([src/lib/redirect.js](../src/lib/redirect.js), tested). |
| **File uploads** | Bucket allows only `jpg, jpeg, png, webp, gif` up to 2 MB (checked by Appwrite and in the form). SVG is not allowed because it can contain scripts. |
| **Referrer** | `strict-origin-when-cross-origin` – full URLs are not sent to other sites. |
| **Passwords & sessions** | Handled by Appwrite (hashed passwords, rate-limited login, httpOnly session cookie). The register form requires at least 8 characters. |

## 5. Secrets

- `.env` is in `.gitignore`; only `.env.example` with placeholders is committed.
- The `VITE_…` values (endpoint, project ID) are **public by design** – Appwrite projects are protected by
  permissions, not by hiding the project ID.
- `APPWRITE_API_KEY` has **no** `VITE_` prefix, so Vite never puts it into the browser bundle. It is used only
  by the local setup scripts and is never deployed.
- The Function does not need a stored key: Appwrite injects a short-lived key with limited scopes into each execution.

## 6. Known limitations (accepted risks)

Being honest about these is part of a security review:

1. **Refill is unlimited by design.** A broke player (< 10 chips) can refill to 1,000. It is play money and only
   possible when nearly broke, so it does not help on the leaderboard (that counts *won* chips).
2. **Fake accounts for invite rewards** are limited (20 rewards, 500 chips wagered each), not impossible.
   A real casino would add e-mail verification or KYC.
3. **Staff are trusted.** An editor can create a promotion (max. 100,000 chips) and claim it. Admins can edit
   any balance. That is the purpose of these roles.
4. **No custom rate limit on the Function.** Appwrite limits logins and requests per IP; a stricter per-player
   limit could be added with a timestamp on the profile.
5. **Session storage on a different domain.** If the site and Appwrite run on different domains and the browser
   blocks third-party cookies, the SDK keeps the session in `localStorage`. The CSP above reduces the risk;
   the full fix is a custom Appwrite domain on the same site (e.g. `api.mycasino.com`).
6. **Hidden games and future promotions are readable** through the API (they are just descriptions). Playing or
   claiming them is refused by the Function.

## 7. Hardening checklist in the Appwrite Console

Set these once when creating the project (Console → *Auth → Security*):

- [ ] Password length ≥ 8, **Password dictionary** on, **Personal data check** on
- [ ] **Session limit** e.g. 10 sessions per user
- [ ] Only the real domains as **Web platforms** (localhost for development + the deployed domain)
- [ ] API key used by the scripts: delete it or reduce its scopes after the setup is finished

## 8. How to demonstrate it

1. **Database refuses direct writes.** Log in on the deployed site, open DevTools → Console and run
   (replace the IDs):
   ```js
   await fetch('https://fra.cloud.appwrite.io/v1/tablesdb/casino/tables/profiles/rows/<your-user-id>', {
     method: 'PATCH',
     credentials: 'include',
     headers: { 'content-type': 'application/json', 'x-appwrite-project': '<project-id>' },
     body: JSON.stringify({ data: { balance: 1000000 } })
   }).then((r) => r.status)   // -> 401
   ```
2. **The Function refuses cheating.** In the Appwrite Console → Functions → *casino* → Executions you can see
   requests and their status codes; a bet over the limit returns 400 *"Maximum bet is …"*.
3. **Automated tests.** `npm test` runs every attack from section 3 against the real Function code.
